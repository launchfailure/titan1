# Supply-Chain Integrity

Titan is used in forensic / incident-response contexts where its output may be
**evidence**. That makes the integrity of the tool itself part of the product:
a consumer must be able to verify that the binary they run is the one built from
this source, unmodified. This page describes the SBOM, reproducible builds, and
release signing that support that.

## SBOM

A CycloneDX 1.5 SBOM is generated by [`tools/gen_sbom.py`](../tools/gen_sbom.py)
and committed at [`sbom.cdx.json`](sbom.cdx.json). It lists the application
component (pinned to the release version) and the optional dependencies (the
runtime core has an empty `install_requires`, so the SBOM is small by design).

The SBOM is **deterministic**: it omits a wall-clock timestamp and derives its
serial number from the version, so regenerating it for the same version yields
byte-identical output — you can diff it against the committed copy.

```bash
python tools/gen_sbom.py            # regenerate docs/sbom.cdx.json
```

## Reproducible builds

The distribution is built with `SOURCE_DATE_EPOCH` pinned so the sdist/wheel are
byte-reproducible across build hosts:

```bash
export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)
python -m build
python tools/repack_sdist.py dist/*.tar.gz
```

The wheel is reproducible from `python -m build` alone — `bdist_wheel` honors
`SOURCE_DATE_EPOCH`. The sdist is not: setuptools stores each tar member with
its **filesystem** mtime (at sub-second precision), which encodes the moment
the build host checked out or generated the file. The
[`tools/repack_sdist.py`](../tools/repack_sdist.py) step erases exactly that
variance — member mtimes set to `SOURCE_DATE_EPOCH`, ownership and modes
normalized, members sorted, gzip timestamp zeroed — while verifying the file
contents are preserved byte-for-byte. The release workflow runs the same step,
so an independent builder running the three commands above gets the published
artifacts.

Because the core has no compiled extensions and no runtime dependencies, a
reproducible build is achievable end-to-end: two independent builders producing
identical artifacts is the verification that the published wheel matches this
source.

## Signed releases

Release artifacts are signed with [Sigstore](https://www.sigstore.dev/)
(keyless, OIDC-backed) in the release workflow, producing a `.sigstore` bundle
per artifact. Verify a downloaded wheel with:

```bash
python -m sigstore verify identity \
  --cert-identity <workflow-identity> \
  --cert-oidc-issuer https://token.actions.githubusercontent.com \
  titan_decoder-<version>-py3-none-any.whl
```

## Release workflow

[`.github/workflows/release.yml`](../.github/workflows/release.yml) ties these
together on a tag push: it regenerates and diffs the SBOM (failing if it drifts
from the committed copy), builds reproducibly with a pinned `SOURCE_DATE_EPOCH`,
signs the artifacts, and uploads the wheel, sdist, SBOM, and signatures as
release assets.

## What this protects (and does not)

Covered: detecting a tampered or non-reproducible build, and providing a
verifiable bill of materials — the supply-chain concern that is explicitly *out
of scope* for the runtime [threat model](THREAT_MODEL.md) (which assumes the
engine source is trusted). Not covered: compromise of the signing identity or of
GitHub's OIDC — those are trust roots, not things this repo can defend against.
